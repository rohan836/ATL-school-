Projects follow the curriculum from computing basics to a safe capstone. Use 60-minute sessions, with a paper/offline fallback for every build. Do not introduce a complex tool before students understand the problem.

Month 1 — My Computer Map

Challenge: What happens between pressing a key and seeing something on screen?
Build: A poster or diagram showing input devices, processing, output, memory/storage and common software. Students create a practice folder with meaningful filenames.
Steps: inspect approved devices; sort components by role; trace input → processing → output; distinguish RAM from persistent storage at a simple level; organise sample files; review login and privacy rules.
Success evidence: a correct labelled diagram, a tidy sample folder, and one safety rule explained.
Fallback: printed component cards and paper file icons.

Month 2 — Algorithm Playbook

Challenge: Can another team follow your instructions without guessing?
Build: Instructions for a simple maze, paper robot, sorting task or classroom routine.
Steps: decompose the goal; order steps; test with a partner; find an ambiguity; revise; draw a flowchart or make a short block program if available.
Success evidence: another team can follow the algorithm and the student describes one debugging change.
Fallback: floor-grid robot using cards.

Month 3 — Tiny Interactive Program

Challenge: Can a small program respond predictably to a user or situation?
Build: A greeting, short quiz, choice-based story or classroom reminder using blocks or a tiny Python starter file.
Steps: predict the output; change text/value; introduce a named variable; if ready, add a simple condition; test a normal and unusual answer; explain each instruction.
Success evidence: a student-modified program and an explanation of what changed.
Fallback: paper code cards and a human “computer” that follows instructions literally.

Month 4 — Classroom Data Story

Challenge: What can a small table tell us without guessing?
Build: A tally/table and chart from fictional data or voluntary non-identifying observations approved by the teacher.
Steps: decide a question; create categories; count examples; check missing or unclear values; create a bar chart; write one claim supported by a count.
Success evidence: table, chart and claim, plus a note that the dataset is small and limited.
Fallback: physical tokens and graph paper.

Month 5 — Rules or AI? Explorer

Challenge: How can a computer choose an answer, and how might it be wrong?
Build: Compare a fixed decision tree with a paper classifier built from fictional cards, or inspect a teacher-controlled beginner demo.
Steps: choose simple categories; label examples; use visible clues; test new cards; record correct and incorrect guesses; improve one rule/example; explain the simulation's limits.
Success evidence: at least five tests, one recorded error, one improvement and a clear distinction between a paper simulation and a trained model.
Fallback: all-paper activity. No camera, external account or live AI tool required.

Month 6 — Helpful Classroom Prototype

Challenge: What small classroom problem can be improved with a transparent tool?
Build options: a rules-based quiz, a study checklist, a plant-care decision tree, a book-category organiser using fictional titles, or a paper classifier. A non-AI solution is fully acceptable.
Required project brief: problem; intended user; how the prototype works; at least three test cases; one change made after testing; one limitation; privacy/safety rule; and the place where a person checks the result.
Assessment: judge reasoning and test evidence, not complexity or device access.

General rules

Use fictional, teacher-prepared or properly approved data. Do not upload student names, images, voices, locations or school records to public AI services. Generated or classified output is a suggestion, not guaranteed truth. Every team member must explain one part of the build.
