# Class 9 — AI & Computing Curriculum

**Duration:** 6 months · 12 sessions per month · 72 sessions total. **Core period:** 60 minutes per session; optional 15-minute extension. **Sections:** C and D share this curriculum; this is the single common copy.

## Course goal
Use software-engineering and experiment-design habits to build and evaluate modest data/AI systems with responsible, independent project work.

## Learning outcomes
- Write modular, testable Python and document changes.
- Prepare data and prevent train/test leakage.
- Justify evaluation metrics and analyse errors.
- Explain RAG and bounded tool use; deliver a reproducible, responsibly reviewed capstone.

## Month-by-month project briefs

### Month 1 — Programming practices
**Concepts:** Functions, modules, data structures, file I/O, exceptions, tests and version-control concepts.

**Build:** Build a small utility with readable modules, input validation, simple assertions/tests and a short change log.

**Evidence:** project artefact, test record, explanation and one limitation. Use paper/offline alternatives where needed.

### Month 2 — Data preparation
**Concepts:** Data dictionary, missing/outlier/duplicate values, transformations, feature design and reproducible analysis.

**Build:** Audit a modest approved dataset, justify cleaning and feature choices, document assumptions and preserve an unchanged source copy.

**Evidence:** project artefact, test record, explanation and one limitation. Use paper/offline alternatives where needed.

### Month 3 — Model building and experiment design
**Concepts:** Baseline, features/labels, train/validation/test idea, leakage and controlled comparison.

**Build:** Define a task, baseline and test plan before modelling. Identify columns that leak the answer or unavailable future information.

**Evidence:** project artefact, test record, explanation and one limitation. Use paper/offline alternatives where needed.

### Month 4 — Evaluation and error analysis
**Concepts:** Confusion matrix, precision/recall, regression error, class imbalance, overfitting and generalisation.

**Build:** Choose appropriate metrics, inspect errors, discuss bias/limitations and report test context rather than only a headline score.

**Evidence:** project artefact, test record, explanation and one limitation. Use paper/offline alternatives where needed.

### Month 5 — Modern AI systems
**Concepts:** Transformer concept, tokens/embeddings/attention, RAG, bounded tools and untrusted input.

**Build:** Build a source-limited answer flow that displays retrieved passages, handles missing evidence and treats retrieved text as untrusted.

**Evidence:** project artefact, test record, explanation and one limitation. Use paper/offline alternatives where needed.

### Month 6 — Independent capstone
**Concepts:** Milestones, iteration, reproducible tests, privacy/fairness/security and communication.

**Build:** Deliver a scoped project with baseline, fair evaluation, iteration, README/report, risk review, demo and individual reflection.

**Evidence:** project artefact, test record, explanation and one limitation. Use paper/offline alternatives where needed.

## Assessment and teacher guide

### Formative assessment
Use prediction questions, concept checks, code/algorithm tracing, test logs, observation and short exit tickets. Evaluate understanding—not speed, polish, device access or whether a model always gives a correct answer.

### Capstone rubric (20 points)
Score each category 0–4: problem/plan; understanding; build and individual contribution; testing and evidence-based improvement; responsible use and communication. A 0 means no evidence yet; 2 means developing with partial evidence; 4 means clear, accurate and independently justified evidence. Use the rubric formatively and adapt for accessibility.

### Minimum project evidence
- A clear problem and chosen approach.
- Program, notebook, physical artefact or explicitly labelled paper simulation.
- Test cases/results appropriate to the grade.
- One issue or limitation identified and one change made because of evidence.
- A short explanation of privacy, fairness or reliability, including where a person checks the result.
- Each learner explains their own contribution.

### 60-minute lesson rhythm
5 min retrieval/challenge · 10 min explanation/demo · 25 min build/investigation · 10 min testing/debugging · 10 min explanation/exit ticket. Adjust pace; do not skip testing or safety to finish a build. An optional 15-minute extension may support additional practice or stretch work.

### Differentiation
Support: starter templates, worked examples, fewer features, sentence frames, paired tracing. Core: build/modify, test multiple cases, record and fix an issue. Extension: compare approaches, add edge cases or justify a metric. Accept spoken, written, diagram-based and accessible demonstrations.

### Safety and responsible AI
Use school-approved tools and teacher-prepared, fictional, public or approved data. Never upload identifiable student names, faces, voices, locations, records or private work to public AI tools. Do not use models to classify real students by sensitive traits or make consequential decisions. Check factual claims against approved sources. No GPU, paid account, webcam, cloud service or public AI account is a prerequisite. Provide paper/offline alternatives. Keep any tool use transparent, permission-limited and under human supervision.

### Teacher preparation
Check devices, software, permissions and connectivity; prepare a known-good example and an offline alternative. Ask students to predict, test unusual inputs, record errors and explain changes. Follow school safeguarding, privacy, copyright and acceptable-use policies.

### Student reflection
What problem did we solve? How does it work? What did tests show? What failed or surprised us? What did we change and why? What should users not assume? What data/permissions need protection? Where must a person review the result?

## Grade-specific implementation guidance

### Technical expectations
Use moderate datasets, simple local execution, and teacher-approved libraries. GPU and cloud use are optional, not prerequisites. Use a baseline before adding model complexity. Never use private student data, uncontrolled autonomous agents, or tools with access to accounts, shell commands, or sensitive files. Source-grounded systems must distinguish retrieved facts from generated wording.

### Project pathway
Possible projects include a data-quality checker, a small environmental-data predictor, a fictional-item classifier, or a question-answering prototype over teacher-approved school guidance that displays its source. A rule-based solution is acceptable when it fits the problem better than AI.

### Teaching and safety
Students should justify the problem and technique, report unsuccessful trials, and keep test data separate from training decisions. Review privacy, fairness, copyright, security, and human oversight before public demonstration. Outputs with real-world impact need adult review and are outside the course's autonomous scope.

### Success standard
Evaluate whether the student can reproduce the result, explain trade-offs, reason from test evidence, and state where the system may fail—not merely whether a model runs.
